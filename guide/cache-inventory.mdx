## 1. 总表

| 缓存 | 放在哪 | 上限 | 全 A × 3 年大约 |
|------|--------|------|-----------------|
| 全市场面板 | 进程，按股票池一份 | 预热过的池子都留着 | **80–160 MB** |
| 日 K 本地 | 进程 | 512 条，写入后 30 分钟 | 满额约 **50 MB** |
| 日 K Redis | Redis `quant:bars:` | TTL 24 小时 | **400–500 MB** |
| 买卖信号 | 进程，跟着面板里的股票对象 | 随面板对象；买点日表最多 8 份 | 金叉/死叉约 **55 MB** + 买点表 **1–2 MB** |
| 市场辅助 | 进程一份 | 1 份 | 日历/行业/停牌/股本约数 MB～十几 MB；涨跌停紧凑数组约 **80 MB** |
| 回测报告 | 进程内，按任务编号 | 无上限，重启清空 | 单次任务数 MB～数十 MB，随成交笔数涨 |

现金、持仓、按手取整后的成交**不进**信号缓存和辅助缓存。摘要进 `bt_job`。成交和净值曲线只留在 `reportCache`，进程退出后没有。

## 2. 全市场面板

按股票池放在进程里，键是 `universeId`。

```text
内存面板
  universeId, from, to, forwardAdjust, loadMs, requested, loaded, failed
  series: 每只股票一条
每只股票
  code
  epochDays      // 交易日（epoch day）
  open
  close
```

面板里没有 high、low、volume。`estimateCloseBytes()` 只统计收盘价数组（约 30 MB）。开盘和日期与之同量级，加上数组头后合计 80–160 MB。

面板价锚在库内最新 `cum_back`。回测另按结束日乘每股系数做点时前复权，任意结束日只要落在面板区间内都能复用同一份数组。系数为 1 时不拷贝。复权因子表在启动预热时装进内存。

组合回测在股票池、复权方式和区间被面板覆盖时直接复用这份数组。冷加载优先读本地 DuckDB（`data/market.duckdb`：日 K、复权、涨跌停、日历、行业、停牌、ST、流通股本、用到的指数）。文件还没有数据时仍走 MySQL。

## 3. 日 K 二级缓存

配置：`quant.cache.local-max-entries`（512）、`quant.cache.ttl-hours`（24）、`quant.cache.redis-enabled`。

键：

```text
stk:{代码}:{前复权 1/0}:{from}:{to}
idx:{代码}:{前复权 1/0}:{from}:{to}
```

Redis 实际键前缀为 `quant:bars:`。

每条缓存是一只股票一段区间的日 K。

```text
code, index, forwardAdjust, from, to
bars: List<BarRow>
BarRow
  date: String
  open, high, low, close, volume: double
```

本地条目是 Java 对象图，单票三年大约 100 KB。Redis 存的是 JSON，单票三年约 55 KB，全 A 加 Redis 开销后约 400–500 MB。统计：`GET /api/v1/cache/stats`。

这一层主要服务于单票加载和预热。面板已经命中时，组合回测不再读它。

## 4. 买卖信号

全进程共用一份。

买卖标记由 ta4j 0.16 的指标算完后写入。K 线对象只在第一次预计算时存在，不算进下面的占用。热路径和第二次回测只读布尔数组。

外层按面板里的股票对象索引。对象还在面板里才命中；对象被回收后条目消失。换初始资金、仓位、手续费不会另建一份。

参数键：

```text
shortMa|longMa|buySignal|sellSignal|sellOnIndicator|日历长度|日历首日|日历中位日|日历末日
```

```text
预计算标记
  barAtCal       // 日历下标 → 该股票 K 线下标，缺失为 -1
  buy            // 下标是 K 线（昨收确认日）
  sell
  strength
  momentum       // 仅 UNIVERSE_RANK；其他规则为空
```

另有按日买点表，最多 8 份，参数或首只股票对象变化会换键；超过 8 份时清空再写。

```text
String[][]     // [日历下标] = 当日有买点的代码
```

买点表里的代码和面板里的股票代码是同一批对象，只多了引用。`UNIVERSE_RANK`（几乎每天全中）不建这张表，买入仍扫全池。

全 A、750 日、金叉/死叉：每只股票约 11 KB（日期对齐 3 KB + 两个 boolean 数组 1.5 KB + 强度 6 KB），合计约 **55 MB**。买点表约 **1–2 MB**。排序买入再加每只股票一条动量数组，大约再 **30 MB**。

## 5. 市场辅助数据

启动预热时装入一份，覆盖预热股票池和预热区间。没有按请求拼的缓存键。

请求的起止日落在这份区间里，且代码都在预热名单中时，直接使用这份内存。因子成分是全市场的子集，因此命中。超出预热区间，或出现名单以外的代码时，按该次请求读 DuckDB，读完不另存。

当前简称里的 ST 随这份数据一起装入。只有回测打开「排除 ST」时才用来挡买入；涨跌停板幅仍按戴帽区间，不按当前简称。

里面有这些表：

```text
limitsByCode: Map<代码, 升序日期 int[] + 涨停 double[] + 跌停 double[]>
alwaysSt: Set<代码>
stRanges: Map<代码, List<[开始日, 结束日]>>
suspendRanges: 同上
floatShares: Map<代码, NavigableMap<epochDay, 股数>>
tradingDays: int[]
industryByCode: Map<代码, 申万一级行业>
```

日历、行业、停牌区间、股本变更点通常是数 MB 到十几 MB。涨跌停是每只股票三条紧凑数组（日期、涨停价、跌停价）。全 A × 750 个交易日大约 80 MB，不再按日建 Map。`stRanges` 从 `st_hat` 装入，给缺公布价时的板幅用。`alwaysSt` 按当前简称装入，只在回测打开排除 ST 时参与挡买入。加载日志里的 `limits=`、`st=`、`suspend=`、`floatPts=` 是实际行数，改估算时以日志为准。

## 6. 回测报告

键是 `jobId`。没有条数上限，也没有过期，进程退出才清空。

```text
报告
  收益、回撤、夏普、拒单计数、loadMs、computeMs
  equityCurve: 日期、权益、基准权益、回撤
  trades: 代码、方向、日期、价格、数量、金额、盈亏
  期末持仓快照
```

库里只留 `bt_job` 的请求和指标摘要，成交笔数是一个数字，没有逐笔。成交、净值曲线、期末持仓只在这份内存里。进程退出后分页接口拿不到成交。任务变多时缓存会一直涨，后续若加淘汰，要改本节的「无上限」。

## 7. 还不在缓存里的数据

| 数据 | 原因 |
|------|------|
| 当日现金、持仓、成交数量 | 依赖本次资金、仓位、费率，不能跨任务复用 |
| 因子组合的逐日成分 | 仍用因子最新一个信号日的代码列表 |
| 均线原始窗口和 | 只保留算完的买卖标记和强度，不保留每天的均线值 |
